# Introdução

A camada Tool representa o nível mais baixo da arquitetura lógica do Agent OS.

Enquanto os Agents tomam decisões e as Skills implementam capacidades, as Tools executam operações técnicas de forma determinística.

Uma Tool nunca interpreta objetivos, nunca decide estratégias e nunca possui conhecimento de negócio.

Sua única responsabilidade é executar uma operação específica e retornar um resultado padronizado.

---

# TL-001 — Tool

## Objetivo

Representar o componente executor da arquitetura.

Toda Tool implementa exatamente uma operação técnica reutilizável.

É a única camada autorizada a interagir diretamente com sistemas externos, bibliotecas, modelos de IA, bancos de dados e recursos do sistema operacional.

# Princípios Arquiteturais

Toda Tool deve obedecer aos seguintes princípios:

- executar exatamente uma operação técnica;
- ser determinística;
- não interpretar linguagem natural;
- não conhecer regras de negócio;
- não conhecer Agents;
- não conhecer Skills;
- comunicar-se exclusivamente através da Message Envelope;
- produzir resultados padronizados;
- preservar o trace_id;
- ser reutilizável por qualquer Skill autorizada.


A Tool representa a fronteira entre o Agent OS e o mundo externo.

Toda interação com hardware, bibliotecas, bancos de dados, APIs, modelos de IA e sistema operacional ocorre exclusivamente através desta camada.

---

# Filosofia da Camada Tool

A camada Tool representa a execução técnica da plataforma.

Os Agents decidem.

As Skills organizam.

As Tools executam.

Essa separação garante baixo acoplamento, alta reutilização e permite substituir tecnologias específicas (por exemplo, trocar SQLite por PostgreSQL ou LM Studio por outro servidor de modelos) sem alterar a lógica da plataforma.

# Auditoria Arquitetural

A documentação detalhada de cada Tool individual (por exemplo, **TL-201 — LLM Tool**, **TL-301 — ChromaDB Tool** ou **TL-501 — REST Tool**) será produzida durante a fase de implementação. Nesta etapa, o objetivo é registrar apenas os domínios funcionais, suas responsabilidades e seus limites arquiteturais, fornecendo uma visão suficiente para auditoria transversal e validação da arquitetura.
